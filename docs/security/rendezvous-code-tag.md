# 드롭 — 랑데부 방 태그가 6자리 코드를 새게 한다

**상태: 알려진 약점, 미해결.** 마지막에 처리하기로 미뤄 둔 것.
발견: 2026-08-14, 엔진 테스트를 쓰다 나옴. 대상: `apps/drop/src/lib/rtc/rendezvous.ts`.

## 무엇이 문제인가

방 태그는 코드에서만 유도된다.

```
tag = PBKDF2-SHA256( "local-tools-drop-v2:" + code,
                     salt = "local-tools-drop-v2:room-tag",
                     iterations = 120_000 ) → 128비트
```

이 태그가 공개 Nostr 릴레이의 `d` 태그(kind 30078)로 올라간다. 릴레이를 구독하는 누구나 본다.

두 가지가 겹쳐서 문제가 된다.

1. **코드 공간이 10⁶뿐이다** — `generateCode()`가 숫자 6자리를 낸다(약 20비트).
2. **salt가 고정이다** — 세션마다 달라지지 않는다. 그래서 태그는 코드만의 결정적 함수이고,
   **표를 한 번 만들면 그 뒤의 모든 세션에 그대로 쓰인다.**

10⁶ × 120,000 = 약 1.2×10¹¹회의 SHA-256. 한 번만 치르면 되는 비용이고, 그 뒤로는
릴레이에서 본 태그를 표에서 찾아 **코드를 즉시 알아낸다.**

## 왜 SPAKE2가 못 막는가

`spake2.ts` 머리말이 약속하는 것은 정확히 이것이다 — *"릴레이에 오가는 대화 기록만으로는
코드를 오프라인 대입으로 검증할 수 없다."* 그 약속은 지켜진다. SPAKE2 전사(transcript)로는
코드를 못 캔다.

**태그는 그 전사 바깥의 별도 통로다.** 공격자는 SPAKE2를 깨는 대신 태그에서 코드를 얻고,
그 코드로 **정당한 참가자로서** 핸드셰이크를 완주한다. 프로토콜은 정상 동작하고, 상대만 바뀐다.

결과적으로 남는 방어는 시간뿐이다 — 방의 TTL 5분(NIP-40) 안에서 진짜 상대보다 먼저
응답해야 한다. 이것은 SPAKE2가 주기로 한 "세션당 온라인 추측 한 번"보다 훨씬 약하다.

## 피해

코드를 아는 공격자는 받는 쪽으로 들어가 **남의 파일을 대신 받거나**, 보내는 쪽으로 들어가
신뢰하는 상대인 척 파일을 보낼 수 있다.

## 고려할 수 있는 길 (아직 고르지 않음)

1. **코드를 길게 한다.** 숫자 6자리(≈20비트) → 영숫자 9자리(≈45비트)면 사전 계산이 무의미해진다.
   가장 단순하고 확실하지만, 손으로 부르고 받아 적는 코드가 길어진다 — 이 도구의 편의가 걸린 지점.
2. **태그를 코드에서 떼어낸다.** 호스트가 방 id를 따로 난수로 만들고 코드는 SPAKE2에만 쓴다.
   QR·링크로 주고받는 경로에는 맞지만, **코드만 불러 주는 경로에는 방 주소가 없어진다** — 그 경로가
   존재 이유라서 그대로는 못 쓴다.
3. **둘을 섞는다.** 코드 = 방 id 부분 + 비밀 부분. 태그는 앞부분에서만 유도하고 SPAKE2는 전체를 쓴다.
   코드는 길어지지만 2번의 구조 문제는 피한다.
4. 반복 횟수를 올리는 것은 **해결이 아니다.** 사전 계산은 한 번만 치르는 비용이라 선형으로만 비싸진다.

## 손댈 때 같이 볼 것

- `rendezvous.ts`의 `NAMESPACE`는 이미 `-v2`다. 방식을 바꾸면 `-v3`으로 올려 옛 방과 격리한다
  (구버전 단일 HTML을 내려받아 쓰는 사람이 있다).
- `apps/stack`의 드롭 설명과 `mechanisms.ts`의 도식에 **PBKDF2 반복 횟수가 실측치로 박혀 있다**.
  같이 고쳐야 `pnpm check`가 통과한다.
- `tests/drop-crypto.test.ts`에 RFC 9382 벡터 검증이 있다. SPAKE2 자체는 건드릴 이유가 없다.
